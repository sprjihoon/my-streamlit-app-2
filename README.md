## 🚀 주요 기능

### 💰 실인보이스 관리 (Billing Invoice)
- PDF 업로드 → **GPT-4o AI 자동 파싱** → 구조화된 데이터 저장
- 다중 파일 드래그 앤 드롭 업로드 지원
- 인보이스 항목별 카테고리 자동 분류 (택배비, 포장비, 입출고비 등)
- 납부 현황 추적 (미납/완납), 통계 분석 페이지

### 🧾 영수증(장끼) 관리 (Receipt)
- 이미지 업로드 → **GPT-4o Vision AI OCR** → 거래처/품목 자동 추출
- 수기 영수증 포함, 금액 검산 (단가×수량=금액) 자동 확인
- 확인 필요 항목 자동 표시, 엑셀 일괄 다운로드

### 📋 인보이스 계산서 (Invoice)
- 업체별 물류비 자동 계산 (배송비, 포장비, 출고비, 보관료 등)
- 엑셀 업로드 기반 청구서 자동 생성 및 PDF 출력

### 📝 작업일지 (Work Log)
- **네이버웍스 봇 AI** 연동. 일지모드는 수선모드와 같이 GPT-5.6 Luna Structured NLU(`reasoning_effort=low`) + 서버 상태 머신
- "어제 틸 하차 다섯 개 건당 3만원, 야간"처럼 말하면 업체·작업·단가·수량·날짜·비고를 구조화해 저장
- 같은 모드에서 이번 달 작업실적·업체별·탑N 조회와 목록 번호 수정도 가능
- 누락값은 한 번에 묻고, 나눠 답해도 기존 draft와 병합. 저장 실패 후에도 작성 중 값은 유지
- 과거 단가는 작업명이 정확히 하나일 때만 제안. `개당`과 `총액`을 구분
- 직전 저장 수정·삭제는 방 단위 포인터로 미리보기 후 `네`/`취소`. 같은 확인은 한 번만 실행
- 엑셀 업로드는 모드와 별개로 기존 저장 경로를 사용

### 🧵 수선작업일지 (Repair Log)
- 기존 작업일지(`work_log`)와 **완전 분리**. 인보이스 계산에 넣지 않음
- 바코드 마스터(엑셀/수동/봇)로 업체·제품·옵션을 채움
- 현장은 사진 2장 이상 + 작업·금액만 입력. 항목마다 비고/메모는 선택
- 봇에서 `비고에 급해`, `급건이라고 메모`처럼 저장 중이거나 방금 저장한 수선에 비고를 넣을 수 있음. 직전 기록 수정은 미리보기 후 `네`로 확정
- 웹 `/repair-log`: 수선일지 목록 + 바코드 등록 + 작업/불량 설정
- 웹 수동 추가에서 바코드 검색 시 등록된 업체명·제품명·옵션을 자동 입력
- **같은 작업일지Bot**이 물류 작업일지와 수선을 나눠 저장 (봇을 하나 더 만들지 않음)
- 수선모드에서도 이번 달 수선실적, 업체별, 탑5, 금액순, 지난달 같은 조회 후속질문을 이어서 처리. 신규 입력으로 바꾸지 않음
- 저장 직후 `방금 저장한 거 잘못됐어`처럼 말하면 미리보기 후 확인해야 수정됨
- 봇 사진은 `fileId` → 302 Location에 Bearer를 다시 붙여 다운로드 (자동 리다이렉트 401 방지)
- 상세 규칙은 아래 [수선작업일지 규칙](#-수선작업일지-규칙) 참고

### 🚨 불량일지 (Defect Log)
- `work_log` / `repair_work_log`와 **완전 분리**. `defect_log` 테이블 독립 운영
- 봇 `불량모드`(키워드: `불량모드 시작`, `불량처리`, `불량할래` 등)에서 대화형 입력
- 사진 2장 이상 + 업체·제품·불량명·수량 입력. 바코드 마스터 연동
- **처리결과는 봇이 처리하지 않는다.** 웹 `/defect-log` 페이지에서 수동 선택
- 처리결과 선택지: `업체반송`, `반품`, `기타` (드롭다운 인라인 편집)
- 미처리 건 카운트 통계 제공. 기간·업체 필터
- **바코드 즉시 조회**: 수동 추가·수정 폼에서 바코드 입력 → `repair_barcode` 조회 → 업체명·제품명·옵션 자동 채움 (600ms 디바운스 + 🔍 버튼)
- **일괄 바코드 갱신**: 목록 상단 버튼 → 바코드 있고 업체명·제품명 누락 행 서버 일괄 처리 (`POST /defect-log/auto-fill-from-barcode`)
- 웹에서 수동 추가·수정·삭제, 전후 사진 썸네일 보기 지원

### 🗓️ 연차 관리 (Leave)
- 연차/반차 신청 및 결재 워크플로우 (팀원 → 팀장 → 인사과장)
- 캘린더 뷰, 잔여 연차 자동 계산
- 연차 승인/반려, 네이버웍스 봇 연동

### 📮 우체국 회수신청 (Return Request)

고객 수거지로 우체국 방문수거를 접수하고, 수거송장번호를 받아 목록에 보여 준다.

#### 개발 현황 (2026-09-07 검증)

| 항목 | 상태 |
|---|---|
| 실접수 InsertOrder | 통과. 스프링풀필먼트 `260940699` |
| 공급지조회 GetOfficeInfo | 통과. 계약에 스프링풀필먼트·인프론트·모두의수선 등 10곳 등록됨 |
| 테스트 접수 `testYn=Y` | 통과. 암호문 안에 넣으면 `TESTREGINOAPI`, 우체국에 실제 전송 안 됨 |
| 회수목록 수거송장번호 | 우체국이 `regiNo`를 준 뒤에만 DB 저장 |
| 주소지 별칭 저장/자동입력 | `/return-request`, `/saved-recipients` |
| **운영 접수 경로** | **Railway 싱가포르 → Vercel Seoul(ICN) 중계 → ship.epost.go.kr** |
| 마이크로소포(`microYn=Y`) | ✅ MICRO 박스 선택 시 우체국 API에 `microYn=Y` 정상 전송 |
| 송장조회 상태 정확도 | ✅ 수거일 미래 건 조회 생략 / 수거완료 오표시 자동 복원 / `집하` 단독 오탐 제거 |
| 관리자 접수 삭제 | ✅ `DELETE /kpost-pickup/{id}` — 관리자만 완전 삭제 가능. 목록 삭제 버튼 |

> Railway(싱가포르)에서 `ship.epost.go.kr` 직접 연결 불가(해외IP 차단). Vercel `/api/epost-relay` (Seoul ICN)를 경유해 우체국에 요청을 전달한다.  
> 환경변수: Railway `EPOST_RELAY_URL=https://tillion.io.kr`, `EPOST_RELAY_SECRET=<secret>` / Vercel `EPOST_RELAY_SECRET=<same secret>`

운영 URL: https://tillion.io.kr/return-request , https://tillion.io.kr/kpost-pickup-list

#### 화면

- `/return-request`: 접수 폼. 다음 주소 검색, 별칭 자동입력, 박스·품명, **접수 버튼 1회로 바로 접수** — **모든 로그인 사용자 이용 가능**
- `/kpost-pickup-list`: 전체 목록, **수거송장번호**, 상태 새로고침, 취소, **접수자·접수일시 / 취소자·취소일시** 표시, 관리자 삭제
- `/saved-recipients`: 별칭별 주소지 추가·수정·삭제

주요 동작:
- 저장된 별칭을 고르면 수취인·연락처·주소가 바로 채워짐
- **해당 정보 저장하기**를 체크하면 별칭을 받고, 접수 성공 시 주소지를 같이 저장
- 품명 기본값 의류, 박스 **기본 극소(1kg·45cm)** ~ 특대형, 수량 1~99
- 수거 희망일 선택 범위: **내일(첫 평일) ~ 오늘+21일** (우체국 계약 허용 범위. 캘린더에서 범위 밖 날짜 선택 불가)
- 같은 날짜·주소라도 재접수 허용 (중복 제한 없음)
- 취소는 우체국 `GetResCancelCmd` POST, `reqYmd`는 **접수일(`res_date` → `created_at`)** 사용
- 접수목록에서 **접수자·접수일시 / 취소자·취소일시** 확인 가능
- 회수신청·접수목록·저장된 주소지 모두 **모든 로그인 사용자** 이용 가능
- **송장조회**: 수거일이 미래인 건은 조회 생략. 수거완료 오표시된 건은 신청접수로 자동 복원

#### 우체국 계약·API 매핑

회수신청은 계약소포 **반품소포**다. `api.InsertOrder.jparcel`, `reqType=2`.

| 화면/의미 | 우체국 필드 | 현재 값 |
|---|---|---|
| 공급지코드 | `officeSer` | `260940699` (스프링풀필먼트) |
| 주문처명 | `ordCompNm` | 스프링풀필먼트 (매뉴얼 최대 100바이트) |
| 수취인(반품인) | `recNm` `recTel` `recZip` `recAddr1` `recAddr2` | 접수 폼 값 |
| 센터(회수도착) | `ordZip` `ordAddr1` `ordAddr2` `ordMob` | 동대구우체국 2층 소포실 `41142` |
| 인증키 | `key` | 오픈API신청결과 **소포신청** 인증키 → `EPOST_API_KEY` |
| 보안키 | SEED128 `regData` | 소포신청 **보안키보기** → `EPOST_SECURITY_KEY` |
| 고객번호 | `custNo` | `EPOST_CUSTOMER_ID` |
| 계약 승인번호 | `apprNo` | `EPOST_APPROVAL_NO` |

우체국 관리화면 조회는 **스프링풀필먼트 (`260940699`)** 로 한다. 인프론트(`260537802`)·인포커스로 보면 우리 접수가 안 나온다.

같은 계약의 다른 공급지(인프론트, 모두의수선 등)는 공급지관리에 있어도, 이 앱은 스프링풀필먼트만 보낸다.

#### 중요 사항

- **보안키와 인증키는 다르다.** 캡처의 인증키만 넣으면 우체국이 접수를 풀지 못하고 `custNo 없음`을 준다. 소포신청 **보안키보기** 값이 `EPOST_SECURITY_KEY`여야 한다.
- 우편번호조회·집배코드·공지·우체국명 인증키는 회수신청에 쓰지 않는다.
- `testYn=Y`는 **암호화된 `regData` 안**에 넣는다. 쿼리/폼에만 넣으면 실제 등기번호가 채번될 수 있다.
- 화면의 **테스트 접수** 체크, 또는 키 없음이면 mock/`testYn` 경로다. 목록의 테스트 건은 우체국 실접수가 아니다.
- 실접수는 `regiNo` 10자리 이상일 때만 저장한다. 타임아웃이면 목록에 남기지 않는다. 다시 누르기 전에 우체국·목록을 확인한다.
- 접수 폼 값은 `rec*`로 그대로 간다. 센터 주소가 폼을 덮어쓰지 않는다.
- 반품 상세주소 `recAddr2`는 2글자 이상(동·호수·층). `recMob`은 보내지 않고 `recTel`만 보낸다.
- Railway 필수 변수: `EPOST_API_KEY`, `EPOST_SECURITY_KEY`, `EPOST_CUSTOMER_ID`, `EPOST_APPROVAL_NO`, `EPOST_OFFICE_SER=260940699`, `INFRONT_CENTER_PHONE`. 키는 커밋하지 않는다.
- 암호화: SEED128 ECB, UTF-8. 샘플은 우체국 `SeedSampleCode`, 명세는 `PostParcel_API_MANUAL`.

## 🚂 운영 배포

### 배포 대상

공식 운영은 아래 두 곳만 본다. **`origin/main` 브랜치 푸시로 자동 배포**된다. DB·사진·`OPENAI_API_KEY`는 배포 시 수동으로 바꾸지 않는다. 봇 NLU는 `BOT_NLU_MODEL=gpt-5.6-luna`, `BOT_NLU_REASONING_EFFORT=low`를 사용한다.

| 역할 | 프로젝트 | 주소 | 비고 |
|---|---|---|---|
| 백엔드 | Railway `my-streamlit-app-2` | https://my-streamlit-app-2-production.up.railway.app | `railway.json` + `Dockerfile.backend`. 볼륨 `/app/data` |
| 프론트엔드 | **Vercel `my-streamlit-app-2`만** | https://tillion.io.kr | Root Directory = `frontend`. FastAPI가 아님. **여기만 배포** |
| 사용 금지 | Vercel `my-streamlit-app` | 배포하면 안 됨 | 옛 프로젝트. Git 연결을 끊어야 함 |

### ⚠️ 배포 프로세스 (중요)

**작업 플로우:**

```bash
# 1. feature 브랜치에서 작업
git checkout feat/your-feature
# ... 코드 수정 및 커밋 ...
git add -A
git commit -m "feat: your changes"
git push origin feat/your-feature

# 2. 배포하려면 반드시 main 브랜치로 푸시 (Vercel/Railway는 main만 배포)
git push origin feat/your-feature:main

# 또는 main 브랜치를 직접 업데이트
git checkout main
git merge feat/your-feature
git push origin main
```

**주의:**
- ⚠️ **feature 브랜치만 푸시하면 배포되지 않음** - Vercel과 Railway는 `main` 브랜치만 감시
- ✅ 변경사항을 실서버에 반영하려면 **반드시 `main` 브랜치로 푸시**
- 🔄 푸시 후 1-3분 내에 자동 배포 완료
- 📱 배포 확인: https://tillion.io.kr (하드 리프레시: Ctrl+Shift+R)

헬스 체크:

```bash
curl -s https://my-streamlit-app-2-production.up.railway.app/health
# {"status":"ok","version":"1.0.0"}
```

Vercel에 FastAPI entrypoint(`pyproject.toml`의 `tool.vercel`)를 넣지 않는다. 백엔드는 Railway에서만 올린다.

### 옛 Vercel `my-streamlit-app`에 배포하지 않기

같은 GitHub 저장소(`sprjihoon/my-streamlit-app-2`)에 Vercel 프로젝트가 두 개 붙어 있으면, `main` 푸시마다 옛 `my-streamlit-app`도 빌드를 시작한다. 공식 프론트는 `my-streamlit-app-2` → https://tillion.io.kr 만 사용한다.

**대시보드에서 옛 프로젝트 Git 연결을 끊는다 (필수):**

1. Vercel → 프로젝트 `my-streamlit-app` (뒤에 `-2`가 없는 것)
2. Settings → Git
3. **Disconnect** 로 `sprjihoon/my-streamlit-app-2` 연결을 해제
4. 새 Vercel 프로젝트를 이 저장소로 만들지 않는다
5. 배포 확인은 항상 https://tillion.io.kr 만 본다

코드도 옛 프로젝트 빌드를 막는다.

- 루트 `vercel.json`: 저장소 루트에서 시작된 Vercel 빌드는 항상 건너뛴다
- `frontend/vercel.json`: `frontend/vercel-official-only.py`가 `my-streamlit-app-2` / `tillion.io.kr` 가 아니면 건너뛴다
- 공식 프로젝트 Root Directory는 `frontend` 로 둔다. `frontend/frontend` 경로로 설치하지 않는다
- 공식 프로젝트는 System Environment Variables 접근을 켠다. `VERCEL_PROJECT_PRODUCTION_URL`이 `tillion.io.kr`이면 빌드한다
- 시스템 변수가 꺼져 있으면 공식 프로젝트에만 `ALLOW_VERCEL_FRONTEND_DEPLOY=1`을 넣는다. 옛 프로젝트에는 넣지 않는다

옛 프로젝트 Git 연결을 끊으면 GitHub에 예전 failure 배지가 남지 않고, 빌드 슬롯도 공식 `my-streamlit-app-2`만 쓴다.

## 🤖 봇 모드와 자연어

정해진 단어를 외울 필요는 없다. `수선할래`, `일지 적을게`, `오늘 작업 넣자`, `하나`, `방금 저장한 거 잘못됐어`처럼 말하면 GPT-5.6 Luna가 현재 모드·작성 중 값·직전 저장 여부만 보고 의도를 구조화한다. GPT는 DB에 쓰지 않는다. 일지·수선은 각각 서버 상태 머신이 검증·확인·저장한다. 웹훅에서 NLU는 한 번만 호출하고, 일지모드는 그 결과를 `journal_bot`에 넘긴다. API 오류 시에는 확실한 로컬 파싱만 사용한다.

짧은 모드 명령은 끝 문장부호를 무시한다. `수선`, `수선.`, `수선 .`은 모두 수선모드다. `오늘 수선실적 알려줘`처럼 업무 문장은 모드를 바꾸지 않는다.

일지모드와 수선모드는 같은 영역의 조회·수정을 허용한다. 최근 조회 문맥은 `(user_id, channel_id)`로 유지한다. `업체명`, `업체별로`, `탑5`, `금액순`, `지난달은`은 신규 입력이 아니라 앞 조회를 이어서 본다. 작성 중 draft가 특정 값을 기다릴 때만 그 값으로 채운다. 조회모드는 읽기 전용이다.

| 명령 | 동작 |
|---|---|
| 일지 / 일지모드 / 일지 쓸게 | 작업일지 입력·같은 영역 조회·수정 |
| 수선 / 수선. / 수선모드 | 수선일지 + 사진 2장 이상, 같은 영역 조회·수정. 비고/메모는 선택 |
| 불량모드 / 불량처리 / 불량할래 | 불량일지 입력. 사진 2장 이상 + 업체·제품·불량명·수량. 처리결과는 웹에서 수동 |
| 조회 / 조회모드 | 조회만. 저장·수정·삭제 없음 |
| 이번달수선실적 → 업체명 | 같은 달 업체별 집계. 사진 요청 없음 |
| 수선실적 탑5 업체명 → 금액순 | 수량 기준 상위 업체 후 금액순 재정렬 |
| 금액순 → 지난달은 | 업체별·금액순은 유지하고 기간만 지난달로 바꿈 |
| 모드 종료 / 현재 모드 | 기본상태로 돌아가거나 현재 모드 안내 |
| 기능설명 / 수선입력방법 알려줘 | 전체 안내 또는 입력·조회·수정·가격·후속·엑셀 주제별 설명 |
| 일지 조회 어떻게 해 / 수선 수정방법 | 같은 주제의 다른 물음은 한 안내로 묶음 |
| 엑셀 업로드 방법 / 지난달은 어떻게 물어봐 | 엑셀·조회 후속 안내 |

`오늘 수선실적 알려줘`처럼 실제 조회·수정 문장은 도움말로 바꾸지 않는다. 입력·조회·수정 방법을 물을 때만 주제별 안내를 보여 준다.

직전 저장 수정·삭제는 미리보기를 보여 주고 `네` 또는 `취소`를 받는다. 작성 중인 초안이 있으면 그 초안을 고치고, 저장이 끝난 기록을 명시할 때만 직전 저장을 건드린다. 일지 포인터는 `journal_last_saved_v2`의 `(user_id, channel_id)`다. 날짜가 없으면 Asia/Seoul 오늘, 수량이 없으면 1건이다.

## 📦 입고모드 개발 기획 (2026-09-08 확정)

> **장끼 사진을 올리면 상품을 자동 매칭하고, 직원은 링크에서 실제수량과 제품사진만 확인하며, 이후 불량·수선 결과까지 연결해 화주사에 하나의 실시간 입고현황 링크와 바코드 PDF를 제공하는 시스템.**

이지어드민 입고 Excel 연동·API 연동은 하지 않는다. 단일 장끼 기준으로 개발한다.

### 업무 흐름

#### 오전 입고

1. 네이버웍스에서 `입고` 또는 `오늘 물건 들어왔어` 입력
2. 봇이 화주사 선택 요청
3. 장끼 사진 1장 업로드
4. AI(GPT-4o Vision)가 도매처·상품명·옵션·수량·단가 판독
5. 기존 `repair_barcode` DB와 자동 매칭
6. 봇이 내부 모바일 입고 작업 링크 제공
7. 직원이 링크에서 품목별로:
   - 실제 입고 수량 입력 / 미입고 확인
   - 제품사진 업로드
   - 매칭 실패 상품만 선택 또는 신규 등록
8. `입고 접수 완료`
9. 실제 입고 수량만큼 **바코드 라벨 PDF** 생성

#### 오후 양품화·마감

1. 실입고 상품 `양품화 중` 상태로 작업 시작
2. 불량 발견 시 기존 불량일지에 등록 (입고건 ID 연결)
3. 수선 가능 불량은 기존 수선모드로 처리 (입고건 ID 연결)
4. 회생 불가 상품 `회생불가` 처리
5. `오늘 양품화 마감` → 수량 검증 후 최종 완료
6. 화주사 공유 링크 자동 갱신

#### 봇 대화 예시

```
직원: 입고
봇:  어느 화주사의 입고인가요?

직원: 틸리언
봇:  장끼 사진을 보내주세요.

직원: [장끼 사진]
봇:  상품 7개, 총 28개로 판독했어요.
     기존 상품 5개 자동 매칭, 2개는 확인이 필요합니다.
     아래 링크에서 실제 수량과 제품사진을 등록해주세요.
     [입고 작업 링크]
```

인식하는 자연어 표현: `오늘 물건 들어왔어`, `입고 잡아줘`, `장끼 등록할게`, `틸리언 입고 시작`, `이 영수증 입고 처리해줘`

입고 처리 중 후속 문장: `3번은 한 장 안 왔어`, `2번 상품이 다른 것 같아`, `이거 신상품이야`, `방금 거 수량 5개로 바꿔`, `오늘 입고 마감해줘`, `미입고만 보여줘`

### 장끼 판독 (단일 장끼)

기존 `receipt.py` (GPT-4o Vision) 그대로 재사용.  
추출 항목: 장끼 날짜·번호, 도매처, 상품명, 옵션, 수량, 단가, 금액, 수기 여부, 판독 신뢰도.

- 판독이 애매한 값은 임의 확정하지 않고 `needsReview=true` 표시 후 직원 확인
- OCR 결과는 직원 확인 전까지 초안으로 유지

### 상품 자동 매칭

기존 `repair_barcode` DB 사용. 바코드가 없는 상태에서 장끼 텍스트로 퍼지 매칭:

```
1순위: 화주사 + 도매처 + 상품명 + 옵션 → 자동 연결
2순위: 화주사 + 도매처 + 상품명       → 후보 2~5개 제시
3순위: 이전 매칭 이력(inbound_items)  → 우선 참조
4순위: 매칭 불가                       → 신규 등록
```

신상품과 매칭 실패 상품만 직원 처리. 나머지는 자동 연결.

### 수량 구조

| 시점 | 공식 |
|---|---|
| 오전 | 장끼 수량 = 실제 입고 + 미입고 |
| 오후 최종 | 실제 입고 = 일반 정상 + 수선대기/수선중 + 수선후정상 + 회생불가 |
| 판매가능 | 일반 정상 + 수선후정상 |

수량이 맞지 않으면 마감을 막고 차이를 표시한다.

불량 1개 제품에 여러 불량·수선 기록이 있어도 `defect_case_id` 기준으로 수량은 1회만 집계.

### 입고 진행상태 (단계형)

수선 대상이 없으면 `양품화 중 → 최종완료`로 바로 진행.

## 🧵 수선작업일지 규칙

기존 물류 작업일지와 별도 기능이다. `work_log`에 컬럼을 더하지 않는다.  
수선 건이 인보이스 청구에 섞이면 금액이 틀어진다.

### 핵심 흐름 (봇)

```
사진 2장 이상 전송 (바코드 / 사진)
    ↓  같은 사용자 메시지를 2~3초 모아 한 세트로 처리
바코드 사진에서 코드 읽기 (문자+숫자, 예: ON56S152917)
    ↓
바코드 마스터에서 업체명·제품명·옵션 조회
    ↓
봇: "베으 / 릴리프T / 블랙 맞아요. 작업이랑 금액 알려주세요"
    ↓
사용자: 구멍 1500원  (또는 스팀 / 바느질 1500원 1건)
    ↓
봇: "구멍 / 단순바느질 1,500원 맞아요? 몇 건이에요?"
    ↓
사용자: 1건  또는  네
    ↓
저장. 금액이 없으면 제품+작업 최근(없으면 업체+작업, 없으면 기본) 비용을 같은 방식으로 확인
```

- 작업 글을 사진보다 먼저 보내도 된다. 글을 잡아 두고 사진 2장 이상이 모이면 저장한다.
- `"틸리언 하차 3만원"`처럼 수선이 아니면 기존 작업일지로 보낸다.
- 신호: 수선/불량/구멍/열펜/잡사/세탁/스팀/바느질/손뜨개/보풀/넥라인/오염 등, 또는 사진 첨부 대기 상태.
- 봇은 **작업일지Bot 하나**. 수선 전용 봇을 따로 두지 않는다.

### 사진 2장 이상

네이버 웍스는 사진을 한 통이 아니라 **메시지 여러 번**으로 보낸다. Railway 워커가 4개라 메모리에 모으면 1장씩 끊긴다. **DB 버퍼**에 모은 뒤 5초(+여유 2회) 후 세트로 본다. **2장부터** 처리하고, 같은 세트에 온 여러 장은 모두 저장한다.

| 규칙 | 내용 |
|---|---|
| 바코드 사진 | AI는 바코드가 있는 장만 찾는다. 읽히는 1장이 바코드 사진 |
| 저장 사진 | 바코드를 제외한 나머지를 **보낸 순서**로 `before_image` → `after_image` → `extra_images`. **바코드 사진은 파일로 저장하지 않는다** |
| 0장 읽힘 | 바코드 숫자를 직접 입력받음. 받은 사진은 삭제하지 않는다. 첫 장은 바코드 사진으로 보관 |
| 2장 이상 읽힘 | 더 또렷한 쪽을 바코드로. 애매하면 물어봄. 받은 장은 유지 |
| 사진 1장만 | 조금 더 기다린 뒤 한 장 더 요청 |
| 4장 이상·중복·판독 오류 | 같은 세트는 모두 현재 건에 저장. 다음 건과 섞거나 유실하지 않음 |

수선 전·후 상태를 AI가 판별하거나 검증하지 않는다. `before_image` / `after_image` 컬럼은 호환을 위해 유지한다.

이미지 웹훅에는 `fileId`만 온다. 다운로드는 `GET /bots/{botId}/attachments/{fileId}` → **302 Location** → 스토리지 URL에 **같은 Bearer를 다시 붙여** 받는다. 자동 리다이렉트를 켜면 토큰이 빠져 401이 난다. `fileId`의 `/` 는 URL 인코딩한다.

### 작업·불량·기본비용 마스터

채팅의 비슷한 표현은 아래 정식 명칭으로 맞춰 저장한다.  
웹에서 추가·수정할 수 있고, 봇으로 신규 작업/불량/비용이 오면 마스터에 넣을 수 있다.

**작업 (정식명 → 기본비용, 별칭)**

| 작업 | 기본비용 | 비슷한 말 |
|---|---|---|
| 스팀작업 | 700원 | 스팀 |
| 단순바느질 | 1,500원 | 바느질, 바느질작업 |
| 손뜨개작업 | 1,500원 | 손뜨개 |
| 열펜제거 | 700원 | 열펜작업 |
| 잡사제거 | 700원 | |
| 부분세탁 | 700원 | 물티슈작업, 부분세탁(물티슈작업) |
| 전체세탁 | 1,500원 | 세탁 |
| 보풀제거 | 500원 | 보풀 |

**불량명 (정식명, 별칭)**

| 불량명 | 비슷한 말 |
|---|---|
| 올풀림 | |
| 봉제 불량 | 봉제불량 |
| 구멍 | 구멍수선 |
| 오염 | |
| 열펜 | 열펜자국 |

예: `"구멍수선"` → 불량명 `구멍`. `"바느질"` → 작업 `단순바느질` 1,500원.

### 봇 비용 확인 규칙

1. **메시지에 가격이 있으면**  
   그 가격으로 저장한다.  
   예: `"구멍 단순바느질 1500원"` → `표기된 가격 1,500원으로 저장했습니다.`

2. **가격이 없으면**  
   ① 같은 **업체 + 제품 + 작업**의 수선일지에서 가장 최근 비용을 찾는다.  
   ② 없으면 같은 **제품 + 작업**, 그다음 **업체 + 작업**.  
   ③ 없으면 위 표의 **기본비용**을 쓴다.  
   ④ 없으면 금액을 물어본다.

   확인 문구 예:  
   `{업체} / {제품} {작업} 최근 비용은 1,500원이었습니다. 그대로 저장할까요?`

   - 네/맞아/저장해 → 그 금액으로 저장  
   - 다른 금액 → 말한 금액으로 저장하고, 해당 작업 기본비용도 갱신할 수 있다

3. **신규 작업/불량**  
   마스터에 없는 말이면 새 작업명·불량명으로 추가할 수 있다. 비용이 같이 오면 그 값을 기본비용으로 넣는다.

### 바코드 마스터 엑셀 양식

창고용 **전체상품목록** HTML(`.xls`) 형식 (UTF-8, 14열).  
기준 파일: `전체상품목록_20260908134022_7493229.xls`

| 열 | 헤더 | 용도 |
|---|---|---|
| [0] | **공급처** | **업체명** (화주사. 예: `헤이즐샵1`) |
| [1] | 대표상품 | 안 씀 |
| [2] | 대표상품코드 | 안 씀 |
| [3] | **상품코드** | 상품코드 저장 |
| [4] | **상품명** | 짧은 이름 없을 때 제품명 |
| [5] | **옵션** | 색상/옵션 (`[연청]`) |
| [6] | 옵션관리 | 안 씀 |
| [7] | **바코드** | **키** (예: `ON56S144442`) |
| [8] | **로케이션** | 창고 위치 저장 |
| [9] | **공급처 상품명** | 짧은 제품명 우선 (예: `라라반팔청남방`) |
| [10] | 공급처 옵션 | 안 씀 |
| [11] | 공급처 위치 | 안 씀 |
| [12] | 공급처 연락처 | 안 씀 |
| [13] | **공급처** | **도매처** 저장 (차후 개발용. 예: `줄리`) |

주의:

- `공급처` 헤더가 두 번 나온다. **첫 번째[0] = 화주사(업체명)**, **마지막[13] = 도매처** — 둘 다 DB에 저장.
- 제품명: `공급처 상품명`이 있으면 그것, 없으면 `상품명`.
- 바코드는 EAN 숫자가 아니라 `ON56S144442` 같은 **문자+숫자**다. Code128 디코딩 + 실패 시 Vision OCR.
- 같은 바코드가 다시 올라오면 덮어쓴다.

### 미등록 바코드 (봇)

1. 바코드를 읽었는데 마스터에 없음 → `등록 안 된 바코드예요. 업체명 알려주세요` → `제품명 알려주세요` → (옵션은 있으면)
2. 마스터에 등록한 뒤 이어서 작업·금액 받음
3. 사진을 못 읽으면 바코드 숫자를 직접 입력받음
4. 마스터가 비어도 업체+제품+작업+금액으로 수선일지는 남길 수 있다

### 웹 페이지 `/repair-log` · `/journal-settings`

`/repair-log`: 수선일지 목록만 표시 (탭 없음).

`/journal-settings`: 바코드 등록·작업/불량 설정을 별도 페이지로 분리 관리.

**탭 1. 바코드 등록**
- 통계: 전체 건수 / 전체 금액 / 오늘 건수
- 필터: 기간, 업체, 작업, 불량명, 작성자
- 컬럼: 날짜, 업체명, 제품명, 옵션, 바코드, 불량명, 작업, 수량, 비용, 작성자, 전 사진, 후 사진
- 전/후 썸네일, 클릭 시 크게 보기 (바코드 사진은 상세)
- 수동 추가 / 수정 / 삭제
- 수동 추가 바코드 입력 후 **검색**(또는 Enter)하면 마스터의 업체명·제품명·옵션을 자동 입력
- **엑셀 다운로드 (사진 포함)**: 필터 업체·기간으로 걸린 수선일지와 작업 사진(바코드 사진 제외)을 서버사이드 `openpyxl`로 생성. 시트1 목록+사진, 시트2 업체별 요약. 최대 400건

**탭 2. 작업/불량 설정**
- 수동 등록, 엑셀 일괄 업로드, 목록 검색/수정/삭제, 양식 다운로드

**수선일지 목록** (`/repair-log`)
- 작업명·기본비용·별칭 CRUD
- 불량명·별칭 CRUD
- 봇과 웹 수동 입력이 같은 마스터를 쓴다

메뉴는 작업일지 옆 **수선작업일지**. 인보이스·기존 엑셀 업로드 메뉴에는 넣지 않는다.  
접근: **관리자**와 **패션팀** 전원. 목록·바코드 등록·작업/불량 설정 모두 조회·수정 가능.

### 수동 등록 필수값

**바코드 마스터**

| 항목 | 필수 | 설명 |
|---|---|---|
| 바코드 | 필수 | 예: `ON56S152917`. 중복이면 덮어쓸지 확인 |
| 업체명 | 필수 | `자체제작_베으` 또는 별칭 `베으` |
| 제품명 | 필수 | 짧은 이름 우선. 예: `릴리프T` |
| 옵션 | 권장 | 색상. 예: `블랙` |
| 상품코드 | 선택 | 예: `S152917` |
| 로케이션 | 선택 | 예: `3I-3-2-6` |
| 상품명(긴 이름) | 선택 | 쇼핑몰 긴 제목 |

**수선일지 수동 추가**

팝업은 2열(너비 약 860px). 한 화면에 날짜·바코드·업체·제품·작업·사진이 보이게 한다.  
바코드를 알 때: 날짜(기본 오늘), 바코드 입력 후 **검색**(또는 Enter). 마스터에 있으면 업체명·제품명·옵션을 자동 입력하고, 상품코드·로케이션이 있으면 안내로 보여 준다. 이어서 불량명·작업·비용을 넣는다. 수량 기본 1. 사진·비고는 선택.  
바코드가 없거나 미등록이면: 날짜, 업체명, 제품명을 직접 입력. 옵션·수량·사진은 선택.  
작업/불량명은 마스터 목록에서 고르고, 비용은 기본값 또는 해당 제품 최근 비용을 채운 뒤 수정할 수 있다.
